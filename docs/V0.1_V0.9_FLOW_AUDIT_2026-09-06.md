# TradingGuard V0.1–V0.9 Flow Audit — 2026-09-06

## Purpose
Trace the end-to-end decision/execution path without weakening Risk Guard. The target invariant is that an eligible setup receives an explicit decision and a PAPER position can exist only after the required authorization and execution revalidation.

## Audited chain
V0.1 foundation/API → V0.2 market data → V0.3 indicators → V0.4 strategy → V0.5 Risk Guard → V0.6 backtest → V0.7 Paper → V0.8 dashboard/API integration → V0.9 Auto Stop, Risk Sizing, prospective gate, pending entry, next-open revalidation and autonomous loop.

## Critical findings

### 1. Browser-owned event suppression could stall the autonomous loop
The frontend previously keyed Auto Paper requests to the dashboard-selected completed candle and suppressed duplicate requests locally. This created a second event clock outside the backend and made `MENUNGGU SETUP BERIKUTNYA` ambiguous.

**Correction:** frontend now polls the backend-authoritative cycle on the normal refresh cadence. Backend candle chronology/idempotency is the only decision clock.

### 2. Dashboard selection could corrupt an active PAPER instrument
The Paper account is single-position, but the user can browse another symbol/timeframe. Before this audit, a selected BTC candle could reach processing while an ETH position was open. Stop/exit logic must never consume a candle from another instrument.

**Correction:** the backend Auto Paper loop locks processing to the symbol/timeframe of the open position or pending action. A mismatch fails closed. The frontend continues polling the operational instrument independently from the chart being viewed.

### 3. Duplicate-candle status was not state-aware
The loop returned a generic `Completed candle already processed; waiting for the next completed candle` even when a position was active or an entry/exit was pending.

**Correction:** duplicate responses now explicitly distinguish active-position monitoring, pending-entry revalidation, pending-exit execution, and flat/no-new-candle state.

### 4. Authorization audit state could become stale across account lifecycle
The process-local `last_authorization` snapshot could survive a reset/start boundary until another eligible evaluation replaced it.

**Correction:** a fresh account state (`event_index == 0`, flat, no pending action) clears the authorization snapshot before evaluation.

### 5. Non-finite numeric values were insufficiently rejected in older boundaries
Market candle and V0.5 risk policy/context models could allow NaN/Infinity through comparison-only validation.

**Correction:** market OHLCV and Risk Policy/Risk Context now explicitly require finite numeric values.

## Locked state machine

FLAT + non-eligible strategy
→ NO ENTRY PROPOSAL

FLAT + BULLISH/STRONG_BULLISH completed candle
→ Auto Stop
→ Risk Sizing
→ complete authoritative RiskContext
→ Risk Guard explicit decision

Risk Guard BLOCK
→ RED / ENTRY REJECTED

Risk Guard WARNING
→ YELLOW / ENTRY HELD

Risk Guard ALLOW
→ YELLOW / SIZED ENTRY PENDING
→ next completed candle OPEN
→ execution risk revalidation

Fresh revalidation ALLOW
→ GREEN / PAPER POSITION ACTIVE

Fresh revalidation WARNING/BLOCK/unavailable/invalid
→ RED or YELLOW according to explicit gate result
→ pending BUY cancelled
→ no position

OPEN POSITION
→ no new entry evaluation
→ monitor only the position's locked symbol/timeframe
→ Stop Loss / strategy exit processing

## Invariants
1. STRONG BULLISH is eligible, not automatic permission.
2. Risk Guard is never loosened to obtain ALLOW.
3. `BELUM DIEVALUASI` must not be used as a substitute for an explicit decision after an eligible flat completed-candle event reaches the gate.
4. Pending is not an active position.
5. A position must not be green merely because `open_position` exists; its execution path must have passed the authoritative interlocks.
6. Chart navigation must not change the instrument being monitored by an active/pending PAPER workflow.
7. Frontend refresh is a caller, not the authoritative event clock.
8. No live broker execution is introduced.
