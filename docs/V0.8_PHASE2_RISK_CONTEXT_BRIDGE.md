# TradingGuard V0.8 — Phase 2 Risk Context Bridge

Status: DESIGN LOCK — implementation must remain fail-closed.

## Purpose

V0.8 integrates the dashboard with the authoritative backend without turning React into a second trading engine and without inventing missing risk facts.

## Source-of-truth semantics

- `PaperTradingConfig.position_size_pct` is capital allocation for the paper position.
- `RiskContext.risk_per_trade_pct` is a separate risk fact required by the V0.5 Risk Engine.
- `position_size_pct` MUST NOT be copied, converted, aliased, or otherwise interpreted as `risk_per_trade_pct`.
- The committed V0.7 paper account does not contain a stop-loss/risk-at-stop model, day-start equity baseline, or peak-equity baseline sufficient to authoritatively derive every V0.5 `RiskContext` field.

## Phase 2 decision

V0.8 will not fabricate a complete `RiskContext` from the paper account.

Until all required risk facts have an authoritative backend source, prospective paper ENTRY is fail-closed. The dashboard must report the risk context as unavailable/incomplete rather than substituting zero, a paper allocation percentage, or a hard-coded value.

This is intentionally different from saying that the market condition is bearish or unsafe. It means execution permission cannot be established from the available authoritative facts.

## Boundary rules

1. React may display risk state but must not construct missing risk facts.
2. Unknown or non-finite risk facts are not zero risk.
3. No fallback may weaken a configured `RiskPolicy`.
4. Existing V0.5 `/risk/evaluate` remains the authoritative evaluator when a complete valid `RiskContext` is explicitly supplied.
5. Existing V0.7 paper state-machine semantics remain unchanged.
6. A wrapper/integration layer must not duplicate paper accounting or project pending execution in order to manufacture risk state.
7. `WARNING` and `BLOCK` never authorize a new paper entry; only an authoritative `ALLOW` may do so.
8. Existing pending exits must never be prevented merely because prospective-entry risk context is unavailable.

## Sequencing constraint

Committed V0.7 `process_candle` owns chronology: validate event -> execute due pending action at current candle open -> inspect current strategy/risk -> schedule a future action -> advance event chronology.

V0.8 must not calculate a pre-step paper projection in the frontend or in a duplicate backend engine. If a future version needs risk derived from post-open account state, the paper service should be refactored into explicit internal phases with regression tests while preserving public V0.7 behavior. That refactor is NOT part of this Phase 2 lock.

## Dashboard behavior for V0.8

The Risk Guard should distinguish:

- Market condition: supplied by Strategy Engine.
- Execution permission: supplied only by an authoritative RiskResult.
- Risk context unavailable: execution permission cannot currently be established.

When context is unavailable, show an explicit unavailable/blocked-for-entry state such as `Awaiting authoritative risk context`. Do not display `ALLOW`, a fake percentage, or zero-valued risk metrics.

Paper state and realized performance may still be read from the backend. Reading state does not authorize or trigger a trade.

## Out of scope

Phase 2 does not add:

- stop-loss placement,
- live trading,
- broker execution,
- automatic position-risk derivation,
- fabricated daily-loss/drawdown baselines,
- a new `/paper/step` endpoint,
- frontend trading calculations.

Those require separate design and tests.

## Acceptance gates

Phase 2 passes only if:

- no allocation-to-risk mapping exists;
- missing risk facts fail closed;
- no unknown/non-finite fact is converted to zero;
- V0.5 evaluator semantics are not weakened;
- V0.7 next-open and chronology behavior are not changed;
- frontend contains no trading decision/accounting engine;
- existing backend regression tests pass;
- frontend production build passes;
- README is updated truthfully only after the integration behavior is finalized.
