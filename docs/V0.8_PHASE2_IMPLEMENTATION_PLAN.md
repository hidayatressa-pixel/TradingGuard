# TradingGuard V0.8 — Phase 2 Implementation Plan

Status: READY FOR IMPLEMENTATION

## Goal

Complete dashboard integration without inventing execution permission or risk facts.

## Scope

### 1. Paper state — read only

The frontend may call `GET /paper/state` and render the authoritative backend account if a process-local paper session exists.

If the backend returns the existing inactive/not-started error, the dashboard must render an explicit unavailable/not-started state. It must not auto-start a paper session merely to populate cards.

Displayed values may include only fields returned by `PaperAccount`, such as active state, configured initial capital, cash, realized equity, open position, pending action state, closed trade count, and event chronology.

### 2. Paper performance — read only

The frontend may call `GET /paper/performance` only as a read operation. Values such as realized return, win rate, profit factor, expected value, and transaction costs must come directly from `PaperPerformanceSnapshot`.

No frontend recomputation of trading performance is allowed. Formatting a backend number for display is allowed.

If no paper session exists, render `N/A`/not started rather than fabricated zero performance.

### 3. Risk Guard

Risk Guard remains unavailable for execution permission until a complete authoritative `RiskContext` exists.

The frontend must not call `/risk/evaluate` with guessed values and must not map `position_size_pct` to `risk_per_trade_pct`.

UI copy must distinguish strategy market condition from execution permission.

Recommended state:

- Execution permission: `UNAVAILABLE`
- Reason: `Awaiting authoritative risk context`

This unavailable state must never be visually represented as `ALLOW`.

### 4. Backtest integration

Backtest results may be displayed only after they are returned by `POST /backtest/evaluate`.

For V0.8, do not fabricate a backtest result simply to populate the dashboard. If the dashboard does not yet have an explicit user-triggered backtest workflow with authoritative candle + strategy inputs, render the backtest panel as not run/unavailable.

A future UI action may submit the already backend-sourced candle and strategy arrays to the existing endpoint. That action must preserve timestamp/order alignment and must not recalculate strategy in React.

### 5. Error handling

Dashboard data domains should fail independently where practical. Failure to read paper state must not erase successfully loaded market/indicator/strategy data.

Backend errors must be rendered as unavailable/error states, not converted to zero-valued financial metrics.

### 6. No automatic execution

V0.8 dashboard loading must not call:

- `POST /paper/start`
- `POST /paper/process`
- `POST /paper/reset`
- `POST /risk/evaluate` with incomplete/guessed context

Merely opening or refreshing the dashboard must never create or mutate a paper trading session.

## Implementation order

1. Add independent read-only paper state/performance loading to the existing frontend integration.
2. Render authoritative paper values when available; otherwise explicit not-started/unavailable states.
3. Keep Risk Guard fail-closed/unavailable.
4. Keep Backtest as not-run until an explicit authoritative workflow is implemented.
5. Audit frontend for any remaining local business calculations or fabricated financial values.
6. Run frontend production build.
7. Run backend regression tests locally before Phase 2 PASS.
8. Update README only after behavior is verified.

## Acceptance criteria

- No dashboard-load mutation.
- No fabricated risk context.
- No allocation/risk semantic aliasing.
- No local trade accounting.
- No local strategy/risk decision logic.
- Paper state/performance are backend-sourced or unavailable.
- Backtest values are backend-sourced or not-run.
- Existing V0.5 and V0.7 behavior remains untouched.
- Frontend build passes.
- Backend tests pass.
