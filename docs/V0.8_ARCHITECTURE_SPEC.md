# TradingGuard V0.8 — Dashboard Integration Architecture

Status: design specification for V0.8 implementation.

Source of truth: committed V0.1–V0.7 backend behavior. This document does not change V0.5 Risk Engine or V0.7 Paper Trading semantics.

## Objective

V0.8 integrates the React dashboard with the authoritative backend. The frontend is a presentation/orchestration client only. It must not become a second trading engine.

## Authority boundaries

- Market data: backend authoritative.
- Indicators: backend authoritative.
- Strategy assessment and evidence: backend authoritative.
- Risk decision: V0.5 backend RiskService authoritative.
- Paper execution/accounting: V0.7 backend PaperTradingService authoritative.
- Backtest/performance: backend authoritative.
- React may format and display backend values but must not recreate strategy, risk, execution, accounting, or performance calculations.

MARKET CONDITION is not EXECUTION PERMISSION. A bullish strategy result does not authorize an entry. Paper entry still requires RiskDecision.ALLOW and the existing V0.7 rules.

## Critical semantic rule: allocation is not risk per trade

V0.7 `PaperTradingConfig.position_size_pct` is an allocation/sizing parameter. The V0.7 execution service uses it to calculate target position allocation from realized equity.

V0.5 `RiskContext.risk_per_trade_pct` is a separate risk fact governed by `RiskPolicy.max_risk_per_trade_pct` and its warning threshold.

Therefore V0.8 MUST NOT map:

`position_size_pct -> risk_per_trade_pct`

The committed V0.7 model has no stop-loss/risk-at-stop field from which actual capital-at-risk percentage can be derived. V0.8 must not fabricate this value, hardcode a safe value, or weaken V0.5 thresholds.

Until an authoritative source for `risk_per_trade_pct` exists, any new orchestration that requires a complete RiskContext must fail closed for a prospective entry rather than manufacture an ALLOW decision.

Do not expand V0.8 into stop-loss/trade-management design merely to fill this field. That belongs to a separately reviewed version unless explicitly scoped.

## Existing V0.7 event-order invariant

`PaperTradingService.process_candle()` currently owns sequential paper execution. Its order is:

1. validate the event,
2. execute a pending ENTRY/EXIT due on the current candle open,
3. evaluate the current StrategyResult/RiskResult for a new pending action,
4. update chronology/event index.

V0.8 must preserve this next-open behavior. A wrapper endpoint must not duplicate or silently reorder this state machine.

In particular, if future risk context is derived from account state for the current decision, orchestration must account for any pending action that V0.7 executes at the current open before using post-execution account state for a new entry decision. Do not create two independent paper state machines.

## Risk-context truthfulness

RiskContext fields must come from authoritative backend state with correct semantics. Unknown or invalid state is not zero risk.

Never convert impossible/non-finite/invalid denominators or missing required safety facts into `0.0` merely to satisfy the Pydantic model. Fail closed instead.

Potentially derivable V0.7 facts include:

- `open_positions`: 1 when an open position exists, otherwise 0.
- exposure: may be derived from authoritative open-position/account values only after its denominator and semantics are explicitly defined and tested.
- `trading_enabled`: must reflect authoritative paper/session enablement semantics.

Facts not present in committed V0.7 must not be invented. V0.7 currently does not persist a daily-equity baseline or realized-equity high-water mark, so daily loss and current drawdown require an explicitly reviewed backend state extension if V0.8 needs them.

Any such extension must derive initial values from `PaperTradingConfig.initial_capital`, preserve reset semantics, use realized equity only, and remain compatible with V0.7 regression behavior.

## Frontend integration requirements

The V0.8 dashboard should expose backend-driven sections for:

- Market
- Indicators
- Strategy score/assessment/evidence
- Risk Guard decision/reasons
- Paper Account
- Trade Journal
- Backtest Performance

Requirements:

- no browser-generated market candles used as authoritative data,
- no local strategy scoring,
- no local RiskContext fabrication,
- no local ALLOW/WARNING/BLOCK calculation,
- no local paper state machine,
- no local trade/accounting engine,
- no fabricated performance metrics,
- unavailable backend values render as N/A/Unavailable rather than fake zero,
- simulated/mock market-data disclosure remains visible,
- status must use text/labels as well as color.

## V0.8 implementation gate

Before V0.8 may be committed as a release checkpoint:

1. Existing V0.1–V0.7 backend regression tests remain passing.
2. New integration tests prove frontend/backend contract behavior.
3. Tests prove `position_size_pct` is never interpreted as `risk_per_trade_pct`.
4. Missing authoritative risk facts fail closed and cannot produce ALLOW.
5. Existing V0.7 next-open pending-action behavior remains unchanged.
6. Invalid/non-finite risk state cannot become zero-risk defaults.
7. Frontend production build passes.
8. README is updated to describe the implemented V0.8 behavior and remaining limitations truthfully.
9. Technical audit PASS.
10. Product-owner visual review PASS.

Do not call V0.8 complete before both technical and visual gates pass.
