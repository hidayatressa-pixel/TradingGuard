# V0.9 Auto Paper Orchestration — Design Lock

## Purpose
Connect the already-tested V0.9 components into one backend-owned PAPER auto-entry pipeline without giving the frontend authority to calculate risk or authorize execution.

## Authority
The backend is authoritative for market-derived strategy, Risk Sizing, RiskContext, Risk Guard, pending-entry state, next-open revalidation, and Paper execution.

The frontend may request/evaluate/display the workflow, but it must not manufacture an ALLOW decision, quantity, stop-loss, risk percentage, account facts, or execution permission.

## Operational entry pipeline
For a prospective long PAPER entry at signal event T:

1. Receive an authoritative `StrategyResult`.
2. Require `data_ready` and `BULLISH` or `STRONG_BULLISH`.
3. Receive explicit stop-loss and risk-budget inputs.
4. Use current authoritative Paper `realized_equity` as sizing equity. A client-supplied equity value is not authoritative.
5. Run `RiskSizingService`.
6. Build complete `RiskContext` from Paper state plus the sizing result's actual `risk_per_trade_pct`.
7. Run `RiskService`.
8. Only `ALLOW` may call `schedule_sized_entry` using exactly `RiskSizingResult.final_quantity`, its stop-loss, and the authoritative Paper equity snapshot.
9. The pending entry remains unexecuted until its next event index.
10. At T+1 OPEN, the existing Execution Revalidation Gate recomputes cost-aware risk from actual OPEN/slippage/fees/stop/equity and runs Risk Guard again.
11. Only a fresh `ALLOW` executes the exact pending quantity. WARNING, BLOCK, incomplete context, invalid stop, invalid/non-finite data, or insufficient cash cancel the pending BUY fail-closed.

## No duplicate engine
The orchestration layer MUST call existing services. It MUST NOT copy sizing formulas, Risk Guard rules, Paper accounting, stop-loss execution rules, or next-open calculations.

## Stop-loss source
V0.9 orchestration accepts an explicit positive long stop-loss below the reference entry. Automatic technical stop generation is NOT introduced in this checkpoint.

## Reference entry
The prospective sizing reference entry must be an explicit authoritative market price supplied by the backend workflow. It is a proposal reference only, not an execution guarantee. Actual execution remains next-open and is revalidated.

## Risk budget
Risk budget is distinct from allocation. `risk_budget_pct` MUST NOT be sourced from `position_size_pct`.

## Failure semantics
Any missing Paper account, inactive Paper mode, invalid strategy, invalid sizing request, incomplete RiskContext, non-ALLOW Risk Guard result, stale account state, or scheduling error leaves the account without a new operational sized BUY.

## Legacy boundary
The V0.7 compatibility path may remain for regression compatibility, but the new operational auto-PAPER endpoint/orchestrator MUST use only the authoritative sized-entry path. It MUST NOT call the legacy allocation-based entry scheduler as a fallback.

## Exits
This checkpoint does not add a new exit authorization gate. Existing strategy exits and stop-loss exits remain reduce-risk actions and must not be blocked by prospective-entry availability.

## User-facing explanation boundary
The orchestration result should expose structured facts sufficient for a later Indonesian `Saran TradingGuard` presentation layer: status, whether execution permission was established, sizing, Risk Guard decision/reasons, and whether a sized BUY was scheduled. Human-readable presentation must not override these facts.

## Out of scope
- Real-money trading
- Broker credentials or order APIs
- Automatic stop generation
- Short selling/leverage
- LLM/AI deciding ALLOW/BLOCK
- Frontend-side trading logic

## Technical gate
Before operational PAPER Auto-BUY is considered technically passed:
- orchestration tests prove ALLOW schedules exact authoritative quantity;
- WARNING/BLOCK/incomplete facts do not schedule;
- allocation is never interpreted as risk;
- authoritative Paper equity is used;
- next-open revalidation tests remain green;
- stop-loss and V0.7 regression tests remain green;
- full backend suite passes;
- working tree is clean.
